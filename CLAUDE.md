# NIDIKUMBA CRM — Project Context

Read this before making changes. It reflects a verified code audit (Aug 2026), not assumptions.

## What this project is

WhatsApp AI-powered CRM for NIDIKUMBA, a mattress brand under The Natural Choice Pvt Ltd (Sri Lanka).
Full requirements: `NIDIKUMBA_Requirements_Specification.pdf` (v2.0). Build sequence: `PROJECT_PLAN.md`.

## Real tech stack (verified, not the original spec's assumptions)

- **Backend:** Node.js + Express
- **WhatsApp channel:** Twilio Sandbox (`TWILIO_WHATSAPP_FROM=whatsapp:+14155238886`). The Meta Cloud API path exists in code but is unconfigured/unreachable — `WHATSAPP_TOKEN` is still a placeholder. Twilio is the live channel.
- **Database:** Self-hosted PostgreSQL, NOT Supabase. Realtime updates via SSE, not Supabase Realtime. This means: no Supabase Auth, no automatic RLS-via-JWT — enforce authorization in Express middleware, not database RLS, unless a middleware-based approach proves insufficient.
- **Frontend:** React/Vite dashboard
- **AI:** Claude API. Tool-calling exists since Phase 8. Three tools are wired up: `escalate_to_human` (terminal — returns `{type:'escalate',...}`, no reply text), and two look-up-and-continue tools, `apply_promo_code` and `check_warranty_status` (each resolves to a JSON result fed back to Claude in a second turn so it can phrase a natural reply — see the `LOOKUP_TOOLS` map in `callClaudeWithRetry()`). `callClaudeWithRetry(messages, customer, retries)` takes the full customer row now (not just phone) since `check_warranty_status` needs `customer.id`. A new lookup tool just needs an entry in `LOOKUP_TOOLS` and a line in the tools array.
- **Website:** nidikumba.shop — informational/marketing only, no backend of its own. "Order Now" opens WhatsApp with a pre-filled message (e.g. "I'm interested in Ayu Spring"). All real transactions happen through this one WhatsApp + Postgres system — there is no second order path to reconcile.

## Real database schema (as of last audit — verify before assuming anything changed)

Six tables exist: `customers`, `products`, `leads`, `messages`, `orders`, `staff_users` (Phase 1).

- `customers.whatsapp_number` is the required field; everything else nullable, matching the "phone-first" design principle
- `leads` is the ticket object — extend it, don't create a parallel table. As of Phase 3 it has `ticket_state` (open/closed), `closed_at`, `closed_reason`, `is_returning_contact`, `reopened_from_lead_id`.
- `customers` gained 5 loyalty-stat columns in Phase 3 (`is_loyalty_customer`, `first_purchase_date`, `last_purchase_date`, `total_orders_count`, `lifetime_value`) — needed by Trigger 1, added ahead of Phase 7 since the trigger can't run without them. Marketing-consent fields are still NOT added — those are Phase 7's job.
- `orders.items` is jsonb shaped like `[{"name": "...", "qty": 1, "unit_price": "45000"}]` — **no `product_id` field exists in line items today.** Any code matching a line item to a product must match by `name`, which is fragile (case/typos) but is what the schema allows until `product_id` is added.
- `orders.status` real live values are **seven, not six**: `pending` (the column's own DEFAULT — every order starts here before staff touch the dropdown) plus `new`, `confirmed`, `processing`, `shipped`, `delivered`, `cancelled` from OrdersPage.jsx's dropdown. An earlier version of this note said "six real values" and omitted the DEFAULT itself — applying that as a CHECK constraint in Phase 3 failed immediately against the one live order row. NOT the spec's nine-value list either (`ready_for_delivery`, `out_for_delivery`, `completed`, `returned` do not exist). **"Completed" anywhere in the spec or this codebase means `status = 'delivered' AND payment_status = 'paid'`, not a status value called `'completed'`.**
- `orders.payment_status` real live values: `pending`, `paid`, `refunded`, `failed` (from the dashboard dropdown) plus `partial` (added in Phase 3 for the payment-tracking work Module 3 is building toward) — five total. Single field, no separate payments ledger table yet.
- `orders.lead_id` (Phase 3) links a completed order back to the ticket that produced it; `orders.amount_paid` (Phase 3) tracks paid amount separately from `payment_status`.
- `trg_order_completed` trigger (Phase 3): fires when an order transitions into `status='delivered' AND payment_status='paid'` — closes the linked ticket and updates the customer's loyalty stats. Trigger 2 (auto-priority for a returning loyalty customer, same Appendix A.3) is NOT built yet — Phase 3 only implemented Trigger 1.
- **Real product catalog swapped (migration 015)** — replaced by a real price list from The Natural Choice Pvt Ltd, confirmed directly with the user: **Ayu Sleep 6, Nidikumba Rise, Nidikumba Signature, Nidikumba Ayu Spring**, plus the same two pillow types. **Careful, non-obvious history here**: an earlier draft spec once mentioned "Ayu Sleep 6, Signature Spring, Ayu Spring, Rise" and that was flagged as fictional (it didn't match the DB at the time) — those names are coincidentally close to *this* real catalog, but the specs are genuinely different (different spring types/thicknesses/pricing structure); this isn't the old fictional catalog resurfacing, it's a real, independently-confirmed business catalog swap. The old 3 products (`Bonnel Spring`, `Nidikumba Ayu Spring`, `Nidikumba Ayu Hardback`) are **not deleted** — kept `active=false` for historical order/warranty integrity. The old `Nidikumba Ayu Spring` row was **renamed** to `Nidikumba Ayu Spring (Discontinued)` before the new product of the same name was inserted — **do not ever let two `products` rows share an exact `name` even across active/inactive**: `name` has no UNIQUE constraint anywhere in this schema, and both `handle_order_stock_reservation` (`UPDATE ... WHERE name = v_name`, no `LIMIT`) and `handle_order_completed_warranty` (`SELECT ... INTO ... WHERE name = v_name`, no `ORDER BY`/`LIMIT`) will misbehave on a duplicate name — confirmed by testing a real order end-to-end against the reused name post-migration: stock reservation correctly touched only the active row, and the warranty trigger correctly picked the active row's `warranty_years`. Nidikumba Ayu Spring remains the real premium/flagship tier — used as such in the Phase 2 lead-scoring prompt. **`variants` shape changed**: `{size, height, price}` (height = spring thickness, a real per-order choice under the old catalog) → `{size, dimension, price}` (`dimension` = exact WxL in inches like `"72x36"`, the real per-unit variant now, since each new product has exactly one fixed thickness, named in its `description`). 5 real size categories now, not 4: Single/Double/Queen/King/**Extra Large**. Pillow-top is a flat `pillow_top_addon_price` (LKR 25,000) on top of whichever dimension is picked — not a separately-priced tier — for the 3 products with `has_pillow_top_option=true` (Rise/Signature/Ayu Spring; Ayu Sleep 6 has none, by design — "no pillow top, no soft comfort layer"). `warranty_years=12` for all 4 new products (vs. the schema default of 5, still used by the 3 old ones). A volume discount (2 mattresses = -LKR 1,500, 3+ = -LKR 2,500, no published rate past 3) is applied client-side in `ShowroomOrderModal.jsx` only — not in `ConfirmOrderModal` (LeadsPage.jsx's single-lead-conversion flow only ever creates one line item, so the "2+ mattresses" case can't arise there) and not enforced server-side.
- `products` gained `stock_quantity`/`reserved_quantity`/`reorder_threshold` in Phase 4, tracked **per product line, not per variant** — order items have no `product_id`/size field to match a variant against, only a free-text name. `trg_order_stock_reservation` reserves on confirm, releases on cancel, finalizes (real decrement) on delivered+paid — matches order items to `products.name` via `item->>'name'` (falling back to the older `item->>'product'` key some historical rows used). `GET /api/products/low-stock` (admin/inventory_manager) is the reorder-alert mechanism — it's a pull endpoint, not a push notification; no email/SMS infra exists to alert through yet.
- `orders` gained `delivery_time_slot`/`delivery_driver`/`delivery_confirmation_note` in Phase 4. Both are gated by CHECK constraints: the two scheduling fields require `status IN ('shipped','delivered')` (spec's "Ready for Delivery" status doesn't exist — `shipped` is the real analog), and `status='delivered'` requires `delivery_confirmation_note IS NOT NULL`.
- **Fixed in Phase 4**: `LeadsPage.jsx`'s Convert-to-Order modal (`PRODUCT_OPTS`) used to offer fictional product names ("Bonnel Spring Mattress", "Pocket Spring Mattress", ...) that didn't match `products.name`, and built its order item with a `product` key instead of `OrderModal.jsx`'s `name` key. Both fixed — the dropdown now mirrors the real catalog exactly (same names `analyzeConversation` already extracts into `lead.product_type`), and both order-creation paths use `name` consistently.
- `messages.sender_type` (Phase 5, `'ai'`/`'staff'`, NULL for inbound) — tagged at the two places messages get inserted in `index.js`. Load-bearing: without it, the AI's instant auto-reply would look identical to a real staff response, and every SLA/overdue metric below would measure the bot instead of the human.
- `leads` gained `assigned_staff_id`/`assigned_at`/`sla_deadline` in Phase 5. `trg_new_lead_assignment` (BEFORE INSERT) auto-assigns every new ticket to the active `sales_agent` with the fewest currently-open assigned tickets, and sets `sla_deadline` from the customer's `priority_label` at that moment (high→1h, medium→4h, low→24h — Hot/Warm/Cold renamed to match the real label values). Locked in at assignment time, not recomputed if priority changes later.
- `v_lead_sla_status` (Phase 5) computes `is_overdue` **live** (no scheduler exists) — overdue means the ticket is still open, past its `sla_deadline`, and no `sender_type='staff'` outbound message exists since `assigned_at`. `v_staff_performance` aggregates this per sales agent: open/overdue/converted counts, conversion %, revenue (delivered+paid orders via `orders.lead_id`), avg time-to-first-contact. `GET /api/performance` is role-scoped — sales_agent sees only their own row, admin/viewer see the ranked team view.
- **Not built this phase** (kickoff prompt's deliverable list didn't ask for these, and both need a scheduler this codebase doesn't have): REQ-4.5's proactive push/email alert on overdue, and REQ-4.6's auto-reassignment after 2× SLA. Also not built: the full `staff_activity_log` table (REQ-4.7/4.8, section 7.3) — overdue detection gets what it actually needs directly from `messages.sender_type` instead of a separate audit-log table.
- **5 BI views (Phase 11, Appendix A.6)**: `v_sales_funnel`, `v_channel_attribution`, `v_revenue_daily`, `v_product_performance`, `v_loyalty_summary` — pure reporting, no new tables. Same corrections already established: `status='delivered' AND payment_status='paid'` not `'completed'`, `item->>'qty'` not `'quantity'`, name/product key fallback. `GET /api/reports/:report` (admin/viewer) serves all five. New `/reports` ("Insights") dashboard page — confirmed by hand: created a real order (2× Nidikumba Ayu Spring, LKR 194,000), computed the expected revenue-by-day total via a manual query, and it matched `v_revenue_daily` exactly, which also matched what the page rendered. REQ-8.7's staff leaderboard is NOT duplicated here — Phase 5's `v_staff_performance`/`GET /api/performance` already is it, with real data, since this project built phases in full sequence rather than the fast path.
- **`warranties`/`service_tickets` (Phase 10, Appendix A.7)** — `products.warranty_years` (default 5, applies to every seeded product including pillows, per the spec's own literal instruction; staff-adjustable via `PATCH /api/products/:id`). `trg_order_completed_warranty` creates one warranty per line item on delivered+paid, matching by name (`item->>'name'`/`item->>'product'`) since order items have no `product_id` — confirmed end-to-end: a Bonnel Spring order produced a warranty dated exactly 5 years out, and the AI's `check_warranty_status` tool read that real row back correctly (not a hallucination). `v_warranty_status` computes `effective_status` live (active/expired/voided) — confirmed a service ticket against a warranty I expired manually correctly returned `warranty_valid: false`. `trg_new_service_ticket` auto-escalates `defect`/`delivery_damage` tickets to `priority_score=3` (this system's real 1-3 scale, not the spec's literal `10`) — confirmed the customer's priority actually flipped to `high`.
- **`influencers`/`promo_codes`/`promo_code_redemptions` (Phase 9)** — not in the requirements spec PDF at all (no REQ numbers, no Appendix A schema); built from business rules confirmed directly with the user. `validate_promo_code`/`redeem_promo_code` are real Postgres functions (not just app-code checks); `redeem_promo_code` uses `SELECT ... FOR UPDATE` to serialize concurrent redemptions of the same code — confirmed via a scripted concurrent-request test that a capped code's last slot resolves to exactly one success. `POST /api/promo-codes/validate` and `/redeem` are deliberately **public/unauthenticated** (nidikumba.shop has no backend of its own — anonymous website visitors call these directly), rate-limited via `express-rate-limit`. Fixed a real bug in the process: `app.set('trust proxy', true)` (trust *any* number of hops) let `X-Forwarded-For` be trivially spoofed, breaking IP-based rate limiting on exactly the endpoint it was added to protect — changed to `trust proxy: 1` (exactly one hop, matching the ngrok/single-reverse-proxy topology). Also fixed a genuine PL/pgSQL bug: `validate_promo_code`'s own return column is named `promo_code_id`, colliding with the identically-named table column in an internal query — confirmed as a real ambiguous-column error by running it directly, not a lint nitpick. `apply_promo_code` is a second AI tool (alongside Phase 8's `escalate_to_human`) — unlike escalation, it's a look-up-and-continue tool: the validation result is fed back to Claude in a second turn so it can phrase a natural reply, confirmed working for both the valid-with-discount and already-used cases. Commission payout (`GET /api/influencers/:id/payout`) only counts redemptions manually linked to an order via `PATCH /api/promo-codes/redemptions/:id` — same no-auto-backfill limitation as Phase 7's `campaign_sends.resulted_in_order_id`, since the website has no order-creation path of its own to link automatically.
- **Promo code usage visibility (migration 016)** — a real gap found while building this: `redeem_promo_code` never populated `promo_code_redemptions.customer_id` even when the redeeming phone already matched an existing `customers` row (e.g. someone who'd messaged on WhatsApp before, then redeemed a code on nidikumba.shop). Fixed with a best-effort phone lookup inside the function — never creates a customer (this route is anonymous/public; that would be a much bigger behavior change than a redemption-tracking fix), just links if one already exists. Confirmed with a real redemption: `customer_id` populated correctly with the matching customer's UUID. New `GET /api/promo-codes/:id/redemptions` (admin/viewer/finance) is the read side — per-redemption phone, discount applied, timestamp, linked customer name if any, and linked order status/total if any. `PromoCodes.jsx`'s Codes-tab table rows are now clickable, opening `PromoCodeDetailModal.jsx` (code summary + the full redemptions list). Also fixed a real display bug in that same table: it read `c.times_redeemed`, a column that doesn't exist — silently fell back to `?? 0` every time, masking the bug until the real column (`redemption_count`) was checked against the schema. The previously-built-but-unusable `PATCH /api/promo-codes/redemptions/:id` manual order-link route now has a UI: an inline "Link order" picker per redemption row, filtering `GET /api/orders` client-side by the redemption's phone number — confirmed end-to-end with a real order (customer Somawathi, LKR 57,000) linked to a real redemption of `KOTA12`, the pill updating live, no page reload. The public `POST /api/promo-codes/validate` and `/redeem` endpoints (Phase 9) are the actual integration contract for nidikumba.shop or any other external site — confirmed still working as documented, no changes needed to hand this to a website developer.
- **Staff-side promo code application at order placement** — both order-creation UIs (`ShowroomOrderModal.jsx`'s walk-in flow and `LeadsPage.jsx`'s lead-to-order `ConfirmOrderModal`) now have a "Promo Code" field, via the new shared `PromoCodeField.jsx`. It calls the same public `POST /api/promo-codes/validate` the website uses (live, debounced, keyed to the customer's phone + current cart total) so a staff-typed code is checked under the exact same rules — expiry, redemption cap, already-used-by-this-phone — no separate staff-only validation path. The discount is subtracted from the order total shown before submit. On actual order placement (not on typing): the order is created first at the discounted total, then `POST /api/promo-codes/redeem` is called for real, then the new redemption is immediately linked to the just-created order via the existing `PATCH /api/promo-codes/redemptions/:id` — so a staff-applied code doesn't need the manual "Link order" step the website flow does; it's auto-linked at creation time. Redemption failure after the order is already created is non-fatal (logged, order still stands) — a lost race on a near-cap code shouldn't undo a real sale. Confirmed end-to-end on both flows with real test codes: Showroom order (Ayu Sleep 6, LKR 28,500 → 23,500 after a LKR 5,000 test code) and a lead conversion (LKR 40,000 → 37,000 after a LKR 3,000 test code) — both produced the correct discounted `orders.total_amount`, a redemption row with `order_id` pre-linked, and (for the lead flow) the lead correctly flipping to `won`. In the Showroom modal the discount stacks with the existing client-side volume discount (promo applied after volume, matching how the total is actually computed); in the lead flow there's no volume discount to stack with, since that modal only ever creates one line item. Both the customer Name field (Showroom modal) and the Promo Code field (both modals) now show a live matching dropdown as staff type — Name reuses the same `GET /api/customers?search=` the Phone field already called (matches name OR phone server-side, so typing a name surfaces the same result a phone lookup would); Promo Code filters the already-loaded `GET /api/promo-codes` list client-side by prefix (active codes only), since the codes list is small enough that a request per keystroke isn't worth it.
- **Edit/delete for promo codes** — `PATCH /api/promo-codes/:id` extended beyond its original `max_redemptions`/`expires_at`/`active` trio to also accept `code`, `influencer_id`, and the discount value field matching whatever type the code already is (`discount_percent` for a percent code, `discount_amount` for an amount code). `discount_type` itself is deliberately never editable once a code exists — flipping a code between percent-off and amount-off after real customers may have already redeemed it under the original terms would misrepresent what they actually got; the route 400s if you try to set the field that doesn't match the code's existing type. New `DELETE /api/promo-codes/:id` — hard-deletes only if the code has zero rows in `promo_code_redemptions` (checked explicitly before the delete, not just left to the FK to throw); a code with real redemption history 409s with a message pointing staff at the existing Active/Inactive toggle instead, since that history is audit data that must not disappear (same principle as never letting a product row's `name` collide, or a campaign's `resulted_in_order_id` auto-backfill — this codebase treats "did this really happen" data as something you deactivate, not delete). `PromoCodes.jsx`'s Codes-tab table gained Edit and Delete icon buttons per row (both `stopPropagation`, so they don't also trigger the row's open-detail click); Edit reuses `NewCodeModal` in a dual create/edit mode — in edit mode the discount-type selector is replaced with a plain readonly note explaining why it can't change, all other fields prefill from the existing row. Delete shows a confirmation dialog that surfaces the backend's exact block message verbatim when it fires, so staff see "this code has redemptions" rather than a generic failure. Confirmed end-to-end: edited a zero-redemption code's cap and expiry (persisted correctly), attempted to delete a code with 1 real redemption (correctly blocked with the exact message), then deleted a separate zero-redemption code (succeeded, row removed from the table with no reload).
- **Influencer detail view (orders + per-order commission)** — the Influencers tab's cards were summary-only (aggregate totals from `GET /api/influencers/:id/payout`, no way to see the actual orders behind them). New `GET /api/influencers/:id/orders` joins across `influencers → promo_codes → promo_code_redemptions → orders`, one row per redemption of any of that influencer's own codes, with `commission` computed per order (`order.total_amount * commission_percent / 100`) only when a redemption is actually linked to an order — an unlinked redemption still shows (which code, phone, discount, when) but with no order/commission, same no-auto-backfill caveat as the payout aggregate. Influencer cards are now clickable, opening `InfluencerDetailModal.jsx`: the existing summary stats at top, a table of every order placed with their codes (order #, code, customer, order total, commission, status, date) with a running "Total commission owed" footer that must match the summary card's figure, and a second table for redemptions not yet linked to an order (with a pointer to the promo code detail view's existing "Link order" picker, Phase 9/the promo-visibility work — linking still happens there, not duplicated here). Confirmed end-to-end against two real orders (Namal LKR 139,300, Dilsara LKR 82,500) redeemed via KOTA12 at a 4% commission rate: per-order commission (LKR 5,572 and LKR 3,300) and the table total (LKR 8,872) both computed correctly and matched the summary card exactly.
- **Product-scoped promo codes (migration 017)** — `promo_codes.eligible_product_names TEXT[]` (NULL/empty = applies to every product, matching how `max_redemptions IS NULL` already means "unlimited" on this same table). Deliberately NOT enforced inside `validate_promo_code`/`redeem_promo_code` — those two Postgres functions only ever take a single total number, no line-item concept, and adding array-containment logic there would mean reworking race-safe functions that already work; instead, `whatsapp-backend/index.js`'s new `computeEligibleSubtotal()` matches cart item names against `eligible_product_names` in JS (same fragile-but-established by-name matching every other order-item-to-product link in this codebase already uses, since order items have no `product_id`) and computes the eligible subtotal *before* calling into the unchanged DB functions — so `redeem_promo_code` still receives a single number, it's just now the scoped one instead of the whole cart. `POST /api/promo-codes/validate` accepts an optional `items` array (backward compatible — a caller sending only `orderTotal`, like an older integration, still gets the old unscoped behavior against an unscoped code) and returns `eligibleProductNames`/`eligibleSubtotal` alongside the discount preview; if a scoped code is checked against a cart with zero matching items, validate returns invalid with an explicit "only applies to: X, Y" message rather than a silent zero-discount success. Both dashboard order flows (`ShowroomOrderModal.jsx`, `LeadsPage.jsx`'s `ConfirmOrderModal`) now pass their real cart items into `PromoCodeField` and — this is the part that actually matters — pass `promo.eligibleSubtotal` (not the whole order total) into the real `/redeem` call at submit time, so the persisted `discount_applied` matches what was actually previewed. `NewCodeModal` (create/edit) gained a scrollable checkbox list of active products under "Applies to" — leaving everything unchecked keeps a code unscoped. `PromoCodes.jsx`'s table gained an "Applies to" column (a pill showing product count, or "All products"); `PromoCodeDetailModal.jsx` shows the full eligible list. Confirmed end-to-end: created `RISEONLY20` (20% off, scoped to Nidikumba Rise only), added both Ayu Sleep 6 (LKR 28,500) and Nidikumba Rise (LKR 39,700) to a showroom cart, applied the code, and confirmed by hand that only the Rise line item was discounted (7,940 = 20% of 39,700, not 20% of the full 68,200 cart) — the placed order's `total_amount` (58,760, after both the volume discount and the scoped promo discount) and the redemption's persisted `discount_applied` (7,940.00) both matched exactly what the UI had previewed before submit.
- **Per-mattress promo codes (migration 052)** — some fixed-amount codes are given once per BILL, others once per MATTRESS (`BMICH2500` on two mattresses = LKR 5,000). New `promo_codes_all.discount_scope` (`order` default — every existing code keeps its meaning — or `per_unit`) plus optional `max_units_per_order` (NULL = no cap). CHECKs: `per_unit` only on an **amount** code (20% off each mattress *is* 20% off their total), and a cap only on a `per_unit` code, >= 1. **`promo_codes` is a VIEW over `promo_codes_all` (036)** — caught only by applying to a clone, the first draft `ALTER`ed the view and failed; the view is rebuilt and `trg_soft_delete` recreated (same sequence as 040/046). What counts as a unit is decided in JS (`countEligibleUnits`, by name, like 017): a scoped code counts its own products; an **unscoped per-unit code counts `category='mattress'` only**, so pillows never multiply it; free lines never count. `redeem_promo_code` gained `p_units INTEGER DEFAULT 1` — the old 3-arg signature is **dropped, not overloaded** (a 3-arg + 4-arg-with-default pair makes every 3-arg call ambiguous), so the website's item-less `/redeem` still resolves and gets exactly one unit, the pre-052 result. Multiplication, cap and the never-more-than-the-order ceiling stay inside the locked function; zero eligible units **fails** rather than burning the customer's one redemption on a 0-value row. `/validate` returns `discountScope`/`eligibleUnits`/`countedUnits` and refuses a per-mattress code on a mattress-less cart; `/redeem` counts units server-side from `items` when sent (both order modals now send them); the order-edit promo path and the AI's `apply_promo_code` result carry the scope too. Per bill / per mattress is **locked once a code has a redemption**, same reasoning as `discount_type`. The invoice prints `Promo code BMICH2500 (2 × LKR 2,500)` only when the stored discount is an exact multiple of the code's amount (a subtotal-capped discount keeps the plain label rather than printing arithmetic that doesn't add up); `×` is inside the embedded fonts' Latin-1 subset. Labels everywhere come from `lib/promoFormat.js`. Verified on a production clone: a real showroom-shaped order (2× Ayu Spring + a pillow) stored 5,000 / total 194,000 and the real PDF renderer drew exactly that; the edit-order path gave 3×2,500 under a cap of 3; down migration refuses while a per-unit code exists, then rolls back cleanly and re-applies. **Not yet applied to production.**
- **Custom discount + admin notifications (migration 053)** — staff can give a discretionary discount on an order **on top of** the automatic volume discount (confirmed default: the volume rule stays automatic; this is an extra LKR amount, not an override; no cap, no approval step). New `orders_all.custom_discount`/`custom_discount_reason`/`custom_discount_by`/`custom_discount_at`; CHECK `orders_custom_discount_needs_reason` (an amount needs a reason) and non-negative. `discount_total` now means volume + promo + custom, and `PATCH /api/orders/:id` **recomputes it in SQL after every discount edit** rather than trusting the client's figure — otherwise an edit that only resends volume/promo would silently drop the custom amount (the promo re-redeem correction path was fixed the same way). Applied **last**, after the promo code, so promo validation is unchanged. `custom_discount_by` is always `req.staff.id`, never the body. **The internal-notes line is written server-side** (`customDiscountNote()`: `[Custom discount] LKR 5,000 by <name> (<role>), <date> — Reason: …`, plus `changed`/`reason updated`/`removed` variants), appended via `concat_ws` so it lands after any `notes` the same request wrote; a no-op re-save adds nothing. ## Conventions for this repo

- Migrations live in `migrations/`, one numbered file per change, never a direct `ALTER` against production without a file recording it
- Every new trigger/constraint that touches `orders.status` must use the real six-value vocabulary above — do not reintroduce `'completed'`, `'ready_for_delivery'`, or `'out_for_delivery'`
- Back up the database before running any migration
- One git branch per feature/phase, merged after manual verification — see `PROJECT_PLAN.md` for the verification step per phase

## The one meta-lesson baked into this file

An earlier version of the requirements spec was written from assumptions and conversation history rather than the real code, and it was wrong about the backend, the channel, and the product catalog. It looked complete and confident, which made the errors easy to miss. Treat any documentation — including this file — as something to verify against the running code periodically, not as permanent ground truth.
